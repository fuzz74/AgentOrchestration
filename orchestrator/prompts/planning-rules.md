## Rules for a good plan

1. **Size.** One task = one agent session of roughly 15-60 minutes, ending in a change that can be checked. Split anything bigger. Merge anything trivially small into a neighbour.
2. **Dependencies.** Add a dependency only when a task needs files, findings or interfaces another task creates. Fewer dependencies = more parallelism. Never create cycles.
3. **Contracts first.** When several tasks must agree on an interface or artifact format (types, API shapes, DB schema, analysis catalog, module boundaries), put a small early task that defines the contract and make the others depend on it.
4. **Ownership.** `owns` lists the repo-relative globs (forward slashes, `**` allowed) the task may edit. Two tasks with overlapping `owns` never run at the same time, and a task that edits outside its `owns` is rejected. Keep `owns` tight and non-overlapping for tasks that should run in parallel. Tests the task writes go inside its `owns`. An empty list means the whole repo (the task runs alone). Files every task may touch (lock files, registries) go in `settings.shared`, not in `owns`, so the tasks that edit them can still run in parallel.
5. **Acceptance.** `acceptance` is one command run with PowerShell 7 (`pwsh`) from the worktree root. Exit code 0 means the task meets its check. Prefer a targeted test for coding or a targeted artifact/coverage validator for analysis. Chain steps with `&&`. The command is already PowerShell, so write a script check as plain PowerShell, e.g. `$t = Get-Content README.md -Raw; if ($t -match 'foo') { exit 0 } else { exit 1 }`. Do not wrap it in `pwsh -Command "..."`: the outer pwsh expands `$t` inside the double quotes before the inner one runs, and the check can never pass. After `&&` or `||` only a command may follow, not an assignment: `./build.ps1 && $t = ...` does not parse, so write `./build.ps1; if (-not $?) { exit 1 }; $t = ...`. Plans whose commands do not parse are rejected. Use an empty string only if nothing can be checked automatically.
6. **Self-contained prompts.** The worker sees only: the spec, its own `prompt`, and short summaries from the tasks it depends on. Write each `prompt` so a newcomer could do the task: deliverables and paths, interfaces or artifact contracts, evidence and constraints, and how to verify the result. Set `workerType` only when a task differs from the run default (`coding` or `analysis`).
7. **Ids.** Short kebab-case, unique, e.g. `auth-api`, `db-schema`. They must match `^[a-z0-9][a-z0-9._-]{0,48}$` and become branch names `orch/task/<id>`.
8. **Integration.** If the parts need wiring together at the end, add a final task that depends on them and owns only the glue files.
